# ADR-001 — เก็บข้อมูลโพสต์แบบ Hybrid (preview สาธารณะ + บัญชีสมาชิก MTProto)

สถานะ: **ตัดสินแล้ว** (ผู้ใช้ยืนยัน 25 ตุลาคม 2026) · อ้างอิง: `docs/SPEC.md` §3–4, `data/probe_report.md`

## บริบท
ต้องตรวจว่าเจ้าของช่อง Telegram ที่รับเงิน 87 สัญญา (172 ช่อง, 24.79M MMK/เดือน) โพสต์โฆษณาที่มี `#platinumclubmm` + รูป/ลิงก์ ตามโควตารายวันและเงื่อนไข pin จริงหรือไม่ โดย **ไม่ให้เจ้าของช่องรู้ว่ามีระบบตรวจ** และไม่ต้องขอสิทธิ์แอดมินจากใคร

สอง handoff ก่อนหน้าเสนอทางตรงข้ามกันโดยยังไม่เห็นข้อมูลจริง:
- `HANDOFF.md`: Cloudflare Worker อ่านหน้า `t.me/s/<username>` อย่างเดียว (ไม่ต้องมีบัญชี) — ตั้งอยู่บนสมมติฐานว่า "ลิงก์ทั้งหมดเป็น public channel"
- `TELEGRAM_MARKETING_DASHBOARD_HANDOFF_TH.md`: บัญชีผู้ใช้ Telethon เข้าทุกช่อง บน VPS โดยอิง repo ภายนอก (ตัวหนึ่งไม่มี license)

## ทางเลือกที่พิจารณา
| ทางเลือก | ครอบคลุม | ร่องรอย | ค่าดูแล | เหตุผลที่ไม่เลือกเป็นทางเดียว |
|---|---|---|---|---|
| (ก) Public-only ด้วย `t.me/s/` บน Cloudflare | 39% ของช่อง, 33% ของเงิน, pin ตรวจไม่ได้ | ไม่มี | ต่ำสุด (ฟรี) | ปล่อย 40 สัญญาให้ตรวจมือต่อ และตรวจ pin ไม่ได้เลย |
| (ข) Userbot MTProto ทุกช่อง บน VPS | 100% รวม pin | บัญชี 1 รายปรากฏในรายชื่อสมาชิกทุกช่อง | VPS 24/7, session, FLOOD_WAIT | ใช้บัญชีกับช่องที่อ่านจากภายนอกได้อยู่แล้วโดยไม่จำเป็น เพิ่มโหลดและความเสี่ยงบัญชี; repo ที่สนใจไม่มี license |
| **(ค) Hybrid** | 100% รวม pin | บัญชีปรากฏเฉพาะ ~105 ช่องที่จำเป็น | Worker ฟรี + collector เล็ก 1 ตัว | **เลือก** |

## การตัดสินใจ
1. **Cloudflare Worker + D1 เป็นแกน**: schema, กติกาตรวจ, rollup, dashboard, alert ทั้งหมดอยู่ที่นี่ ไม่ว่าข้อมูลมาจากทางใด
2. **Public collector ใน Worker (cron)**: ช่องที่เปิด preview ใช้ `t.me/s/<u>?q=%23platinumclubmm` (+ `?before=` เมื่อโพสต์ถี่); ทุกช่องสาธารณะและลิงก์เชิญใช้หน้าโปรไฟล์/หน้าเชิญเก็บชื่อและยอดสมาชิกเพื่อตรวจ rename/ตาย
3. **MTProto collector แยกตัว** (Telethon/GramJS, บัญชีสมาชิก 1 บัญชีที่บริษัทควบคุม): เฉพาะช่องส่วนตัว 75 + ปิด preview 27 + เว็บซ่อน 3 และดึง pinned messages ของทุกช่องที่บัญชีอยู่ แล้ว `POST /api/ingest` (HMAC) เข้า Worker ไม่มี DB/UI ของตัวเอง
4. **เขียนเอง ไม่ fork repo ภายนอก**: ความต้องการจริง (contract 1:N channel, quota จาก remark, pin rule, reg) ไม่ตรงกับ repo ที่ประเมินไว้ และตัวที่ผู้ใช้สนใจไม่มี license ให้ใช้เชิงพาณิชย์
5. โพสต์ทุกแถวระบุ `source` และสถานะ `unverifiable` มีจริง — ห้ามสรุป "ไม่ได้โพสต์" เมื่อระบบเข้าไม่ถึง

## ผลที่ตามมา
- ต้องมีบัญชี Telegram สำหรับงานนี้ 1 บัญชี ล็อกอินบนเครื่องที่บริษัทควบคุม และเจ้าของช่องส่วนตัวจะเห็นสมาชิกเพิ่ม 1 ราย (ผู้ใช้รับทราบและเลือกแล้ว)
- มี 2 ส่วนที่ต้อง deploy (Worker + collector) แต่ collector เป็นโปรแกรมเดียวที่ย้ายเครื่องได้ และถ้ามันหยุด ระบบยังตรวจ 67 ช่องสาธารณะได้ต่อ (สถานะที่เหลือกลายเป็น `unverifiable` ไม่ใช่ `missed`)
- ถ้าภายหลังบังคับให้ทุกช่องเปิด preview หรือใช้แค่ช่องสาธารณะ ส่วน MTProto ถอดออกได้โดยไม่กระทบ schema
